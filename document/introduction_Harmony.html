Purpose

Harmony is a project skeleton: a language-agnostic directory structure and a set of maintenance tools, kept in a git repository, from which new projects are made. It is designed for long-lived software developed by a team, and serves equally well for one person, who takes on each role in turn. The structure exists to give:

  1. Clarity about where things live.
    • Role-based work areas.
    • Separation of skeleton, team member authored, machine-made, and depended-upon software.
  2. A safe, predictable build and promotion workflow.

Making a project

A project administrator makes a new project from a clone of Harmony, by taking on the administrator role and running new-project with the name of the new project:

> cd Harmony > ./setup administrator > new-project <name>

new-project makes the new project as a sibling directory of Harmony, then:

  1. Copies the files of Harmony's last commit, leaving out Harmony's git history, untracked files, and uncommitted changes.
  2. Renames 0pus_Harmony to 0pus_<name>.
  3. Adds a line for the new project to shared/tool/version.
  4. Initializes a git repository on the core-developer_branch branch, and commits the copied skeleton.
  5. Adds any remote repositories given as -remote <url>.

Because the new project starts with its own git history, work done in it cannot be checked in to the Harmony skeleton by accident.

Leave the Harmony line in the version file. It records which skeleton the project was made from, so that an administrator can later see what has changed in the skeleton since, and bring the project up to date. The administrator tool skeleton_diff compares a project with a Harmony checkout for this purpose.

Taking on a role

A person works in a project by taking on a role. The roles are administrator, developer, tester, and consumer. From the top directory of the project, run setup with the role:

> ./setup developer

setup starts a new bash shell configured for the role, and leaves the person in the role's directory. The prompt shows the project and the role. exit leaves the role and returns to the shell setup was run from. It is common to have several terminal windows or Emacs shells open, each in a different role.

Python programmers will recognize this as similar to a virtual environment. Harmony calls it the project setup, and the command is setup rather than activate. Unlike a Python virtual environment, there is one setup for each role.

In the new shell, the setup:

  • Sets ROLE, ROLE_HOME and SETUP, and puts <role>/tool on the PATH.
  • Sources the project-wide shared/tool/setup, which sets REPO_HOME and PROJECT, puts shared/tool and shared/authored on the PATH, and sources each project dependency's .init file.
  • Sources shared/authored/setup, when the project has one, for project-specific additions to every role.
  • Changes into the role's directory and sources <role>/tool/setup, the setup customized for that role in this project.
  • When running inside Emacs, copies the environment to Emacs with env_to_emacs.

Tools rely on this environment. Absolute paths are formed from REPO_HOME, and some tools, such as build and promote, refuse to run outside the role they belong to.

Roles and their directories

Each role has a directory at the top of the project. The shared directory holds what all roles use.

Administrator

The administrator keeps the project in step with the Harmony skeleton, maintains the role environments, installs project dependencies, and makes releases. administrator/tool holds the tools for this, among them new-project, skeleton_diff, and archive, which writes an archive of the repository to the scratchpad.

Developer

The developer writes the project's source and builds it.

  • authored/ : Source written by the team. Tracked.
  • document/ : Documents for developers, such as coding and naming conventions.
  • experiment/ : Informal, short-lived trials.
  • scratchpad/ : Untracked. Intermediate build files and the staged products of a build.
  • tool/ : The developer's tools, including build and promote.

Tester

The tester holds the formal tests, including regression suites, and runs them against the work product in consumer/. A developer may keep informal tests in developer/experiment. A test that is to be kept is moved to tester/, which keeps writing code and validating it apart.

Consumer

consumer/ receives the work product when a developer promotes it. It is untracked, apart from its .gitignore, and is treated as a deployment target: files arrive there only through promote, and nothing is built in it. The consumer role uses the work product as its end users would.

Shared

  • shared/tool/ : Tools for all roles, and the project-wide setup. The version command prints the version lines.
  • shared/authored/ : Project-specific additions for all roles. It is on every role's PATH, and may hold a setup that every role sources.
  • shared/project-dependency/ : Software the project uses but did not author. See "Project dependencies" below.

Building and promoting

Building and promotion are separate steps. In the developer role, build makes the work product from developer/authored and stages it on the developer's scratchpad. promote write then copies what changed to consumer/. The result is a promotion candidate, which stays as it is until the next promotion.

Source in developer/authored is grouped into directories named <Namespace>.<Tool>. The suffix names the build component in developer/tool/build_component that builds that directory, such as make for C, or copy for files used as they are. Given no arguments, build prints its usage and the namespaces it found. promote given no arguments prints its commands, among them dry write, which shows what write would copy.

The tester runs tests against the promotion candidate. Tests read from consumer/ and never write to it, though a tester may copy files elsewhere to experiment with them. A developer often has a second window open in the tester role, and cycles through edit, build, promote and test.

After cloning a project

Built products are not tracked, so a fresh clone has an empty consumer/. A team member who needs the work product builds it, taking on the developer role to do so:

> ./setup developer > build <namespace> > promote write > exit > ./setup <role>

The developer documents any project-specific build steps in developer/document/build.html. A fresh clone also lacks the project's dependencies, which each team member installs as described beside each dependency in shared/project-dependency.

Project dependencies

Harmony is language agnostic. When a project uses C, Python, NodeJS, Java, or other software it did not author, the administrator installs that software as a sibling directory of the project and links it in under shared/project-dependency, with an .init file that every role's setup sources to put the dependency into the environment. Installation notes for each dependency sit beside its .init file, so that each team member can repeat the installation after cloning.

The directory comes with a project link to the directory holding the project and its siblings, through which dependencies are linked, and with Python as an example dependency. The steps are given in administrator/document/how-to_add-project-dependency.html.

Directory names

A directory name is a property of each file in the directory, so a full path reads as a description of the file. Because a name states a property of each file, it is rarely plural: when every file in a directory is a test, the directory is named test.

A conventional file system can only approximate a property-based one. Each file sits in one directory, so it receives one property per level of the path. Files sharing several properties can be given a compound name with the properties separated by an underscore, but overlapping groupings cannot be expressed.

When choosing a directory name, prefer properties in this order:

  • Role (administrator, developer, tester, consumer): the role, human or AI, that works with the files.
  • Provenance (authored, made): whether a person wrote the file or a tool produced it.
  • Capability (tool, document, experiment): what the file is for.
  • Lifecycle (scratchpad, stage): how long the file is expected to last, or where it is in promotion.
  • Tracking (tracked, untracked): what version control does with it.

Authored, made, scratchpad, inherited

Files in a directory named authored were written by the project's team. They did not come with the skeleton, nor with the installation of other software, and they typically constitute the project's intellectual property. Build tools treat authored directories as read-only. All source that is built into a promotion or a release is placed in developer/authored.

Files that came with the skeleton are inherited. When the team edits one, such as developer/tool/build, it becomes a customization. New documents go in document directories and new tools in tool directories. Because the Harmony line stays in the version file, an administrator can tell which skeleton files a project has customized and which it has added.

Files in a directory named scratchpad are untracked, so a clone always has empty scratchpads. Tools place intermediate and staged files there, each in its own subdirectory, so a person who knows those names can also use a scratchpad as a temporary directory. The scratchpad tool maintains the scratchpad of the current directory. Note that its clear command deletes everything on that scratchpad.

Documents

Each directory named document holds documents for the role, or the scope, of its parent:

  • document/ : The project as a whole, such as this introduction.
  • administrator/document/ : Maintaining the project skeleton, adding dependencies, and making releases.
  • developer/document/ : Coding standards, conventions, and the build.
  • tester/document/ : Test plans and testing tools.
  • consumer/<namespace>/document/ : Documents released with the work product, such as manuals and API references.

Documents are written in HTML with the RT semantic tags, and formatted by RT-Style, a separate project at https://github.com/Thomas-Walker-Lynch/RT-Style. A document loads RT-Style through a short script block at the top of its head. To write a new document, copy an existing one, keep that block as it is, and type over the contents.

Documents are read in Chrome. With nothing set up, a document loads RT-Style from style.ReasoningTechnology.com. To read without a network connection, or against a local copy of RT-Style, open that copy's Manuscript/setup.html once in Chrome. Chrome then loads RT-Style from it for every local document.

document/writing_tool-script.html gives the conventions for writing tools.

What git tracks

Everything is tracked except:

  • consumer/, apart from its .gitignore.
  • Every scratchpad/, apart from its .gitignore.
  • In shared/project-dependency/, whatever its .gitignore does not list as tracked.
  • Archives, editor backups, and compiled files, as listed in the top-level .gitignore.

Workflow and releases

The project moves forward through a cycle: the developer promotes a candidate, the tester tests it and files issues, and the developer fixes them and promotes again. The core-developer_branch is the branch the core development team works on. When the product manager judges the work product reliable and complete enough, the administrator makes a project release on a branch named release_v<major>, and tags it.

These documents give the details:

  • document/role-and-workflow_product-development.html : The roles, and how their work interacts.
  • document/role-and-workflow_product-maintenance.html : Issues, triage, and patching releases.
  • administrator/document/how-to_release.html : Making a release.
