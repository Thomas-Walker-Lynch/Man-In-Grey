Purpose

A tool is a script a person runs from a role setup to do work on files. This document gives the conventions for how an RT tool presents itself on the command line, reports what it does, and changes files safely. It complements RT-code-format.html, which covers identifier names, layout, and the separation of the CLI() function from the work functions. Those rules apply here and are not repeated.

The conventions serve three needs of the person at the keyboard. They must be able to see what a tool will do before it does it, read afterward what it did, and run it again without harm.

Examples are taken from RT-Style_header_v5_to_v6, the administrator tool that converts RT-Style version 5 document headers to version 6.

The command line

No arguments prints the help

A tool given no arguments prints its help message and exits with status 0. A person who types the bare name of a tool is asking what it does. Nothing on the file system changes.

The first argument is a command

The first argument names a command, written as a word, not a flag. The words help, -h and --help all print the help message. Further arguments, when a command accepts any, follow the command. A command that accepts no further arguments rejects them with an error.

An unknown command prints an error naming it, then the help message, and exits with a nonzero status.

The help message is the module docstring

In Python the help message is the module docstring, printed by print(__doc__.strip()). The documentation at the top of the file and the message the person sees are then the same text, and cannot drift apart. The docstring opens with the tool name, a paragraph on what the tool does, then the usage and one line per command:

Usage: RT-Style_header_v5_to_v6 <command> [file ...] RT-Style_header_v5_to_v6 preview <command> [file ...] help | -h | --help print this message (also printed when given no arguments) project walk the directory tree rooted at $REPO_HOME tree walk the directory tree rooted at the current directory local only the current directory, no subdirectories file <name> ... only the named .html files preview <command> print the log of what <command> would do, change nothing

Scope commands

A tool that acts on files found in a directory tree offers the same four commands for choosing which files:

  • project walks the tree rooted at $REPO_HOME. When REPO_HOME is not set, the command is an error. Otherwise it behaves as tree run from $REPO_HOME, from whatever directory the person is in.
  • tree walks the tree rooted at the current directory.
  • local acts on the current directory only, without descending.
  • file acts on the files named after it.

Only project depends on a Harmony project. The others work anywhere, because the files a tool serves are not always in a project. RT-Style documents, for example, appear in projects and outside them.

Preview

A tool that changes files offers preview, placed before any other command. preview tree prints the log that tree would print and changes nothing. The person reads it, decides, then runs the command without preview.

Preview is not a separate code path. The work functions are given a preview flag and test it only at the point of each action, immediately before writing or deleting. Everything else, finding files, deciding what to do, and logging, runs the same in both modes. A preview log that came from different code could not be trusted to describe the real run.

The log

A tool that acts on files prints a log of each thing it did. The log is for a person reading a terminal, and for that same person reading it again in a scrollback or a saved file later. This is the log of converting the Harmony skeleton documents, with the path on the first line shortened to fit the page:

RT-Style_header_v5_to_v6 project in /home/Thomas/.../project/Harmony converted administrator/document/how-to_release.html converted developer/document/naming_file-and-directory.html converted developer/document/single-file_C-module-and-namespace.html converted document/introduction_Harmony.html converted document/role-and-workflow_product-development.html converted document/role-and-workflow_product-maintenance.html summary: 6 .html files converted to version 6 0 RT-Manuscript_locator.js files deleted 0 .html files already version 6 0 .html files with mentions to edit by hand 0 other .html files left alone
  • The first line names the tool, the command, and the absolute directory the work is rooted in, so a saved log says where it came from.
  • Each action is one line. A fixed-width tag in the past tense says what happened, followed by the path relative to the root. Relative paths keep lines short and make logs from different machines comparable.
  • In a preview the tags read would convert, would delete, and the summary ends with preview only: nothing was changed.
  • A decision not to act is logged too, with the reason in parentheses, as in kept shared/document/RT-Manuscript_locator.js (no version 5 document beside it). A file the tool left alone on purpose must be distinguishable from one it missed.
  • Work the tool cannot do safely is logged with the tag edit by hand, the file, the line number and the line, as in edit by hand .../Document/user.html:83: &lt;script src=..., so a person can go straight to it.
  • A summary of counts ends the log. A count line that would always be zero for a run, such as errors, may be left out when it is zero.
  • Walk directories and files in sorted order, so two runs over the same tree produce the same log.

Errors are logged on their own lines with the tag error, the tool carries on with the remaining files, and the exit status is nonzero when any error occurred. Errors in the command line itself are printed to standard error before any work starts.

Walking directories

A tool walks every directory in its scope, whatever the directory is named. It does not skip directories by name, since a name that means nothing to the tool's author may hold files that matter to its user.

A tool does not follow symbolic links to directories. A Harmony project has shared/project-dependency/project pointing to ../../../, the directory holding all the projects. Following it would send the walk into every neighboring project and around the loop back into this one. In Python, os.walk does not follow such links unless given followlinks=True, so leave that argument out.

Paths

A tool forms an absolute path only by starting from an environment variable that the role setup provides, such as $REPO_HOME. Paths the tool writes into files, and symbolic links it creates, are relative.

An absolute path written into a file is correct for only one view of the file system. Under the subu arrangement, the master user reaches a sub-user's files through a mapped mount at a different absolute path from the one the sub-user sees. A path recorded by one of them is then unreadable, or points somewhere else, for the other. A relative path is resolved from wherever the file is reached, so it is correct in every view.

Changing files safely

Checkpoint first

A tool edits files in place and does not make backup copies. The person checkpoints the project with git before running it, and reviews the result with git diff. Run preview first.

Change only what is recognized exactly

Match the precise form the tool was written to change, in the precise place it occurs. RT-Style_header_v5_to_v6 replaces a locator script line only when it stands alone on a line inside <head>. A mention of the locator anywhere else, such as an escaped example in a manual, is not touched. It is logged for a person to edit.

Keep everything not being changed

Carry over what the edit is not about: the indentation of a replaced line, line endings, file permissions, and every other line of the file byte for byte. After a run, git diff should show the intended change and nothing else.

Running twice does no harm

A second run of the same command finds nothing left to do, changes nothing, and says so in its summary. A tool achieves this by recognizing work already done. The header converter counts a file holding the version 6 block as already version 6 and leaves it alone. A person can therefore rerun a tool to confirm a job is complete, or to finish one that stopped part way.

Before deleting, check nothing still uses it

A tool deletes a file only when nothing remaining depends on it. In testing, the header converter run with file on two of six test documents in a directory deleted the shared locator file while the other four still needed it. The rule now is that a locator is deleted only when no unconverted version 5 document beside it still loads it. Otherwise it is kept, and the log names the documents still using it.

Leave alone what the tool cannot identify as its own

A file with the right name in an unexpected place is not evidence that the tool should remove it. The converter keeps a locator file that has no version 5 document beside it, and logs it as kept, leaving the decision to a person.

Testing a tool

Test a new tool on a copy of real material before it runs on the original. An archive of the project, extracted into a scratch directory, gives realistic files that can be discarded.

  1. Run with no arguments, an unknown command, and each command's error cases, such as project with REPO_HOME unset or file naming a file that does not exist.
  2. Run preview and confirm that nothing changed, for example with diff -r against an untouched copy.
  3. Run each scope command from more than one directory, including from outside any project.
  4. Run each command twice. The second run must report nothing left to do.
  5. Run on part of a job, such as file on some of the documents in a directory, and confirm the rest still work.
  6. Read the diff of a changed file in full.

A skeleton

A Python tool laid out to these conventions begins with #!/usr/bin/env python3, then the Emacs mode line the Harmony tools carry, which sets two-space indentation and no tabs. The rest of the skeleton follows:

""" tool_name What the tool does, in a paragraph. Usage: tool_name <command> [file ...] tool_name preview <command> [file ...] help | -h | --help print this message, also printed given no arguments project walk the tree rooted at $REPO_HOME tree walk the tree rooted at the current directory local only the current directory file <name> ... only the named files preview <command> print the log of <command>, change nothing """ import sys ,os from pathlib import Path def work(dirpa_root ,recursive ,preview): ... def print_help(): print(__doc__.strip()) return 0 def CLI(argv=None): if argv is None: argv = sys.argv[1:] if not argv or argv[0] in ("help" ,"-h" ,"--help"): return print_help() preview = argv[0] == "preview" if preview: argv = argv[1:] if not argv: print("Error: 'preview' needs a command after it." ,file=sys.stderr) return 1 command ,rest = argv[0] ,argv[1:] ... if __name__ == "__main__": sys.exit(CLI())

Exercises

Exercise 1: The bare tool

A tool named tidy deletes editor backup files ending in ~. When run with no arguments it deletes them from the current directory. List what is wrong with that behavior under these conventions, and give the command line it should have instead.

Exercise 2: A log line

A tool prints Processing /home/Thomas/subu/developer/project/Two/document/a.html ... done for every file it looks at, whether or not it changed it. Rewrite the log for a run in which one of three files was changed, one was already correct, and one could not be read.

Exercise 3: A safe delete

A tool replaces each include.css link in an HTML document with an inline style block, then deletes include.css from the directory. Describe the run in which this breaks a document, and the check that prevents it.
