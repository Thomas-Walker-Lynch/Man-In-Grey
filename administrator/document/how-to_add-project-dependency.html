Project dependencies

A project dependency is software the project uses but did not author: a language toolchain, a library, a tool, or another project. A dependency is installed outside the project, as a sibling directory of it, and is linked into the project under shared/project-dependency.

Getting an arbitrary piece of software working is different every time, so the administrator is free to do whatever a dependency needs inside shared/project-dependency. The skeleton relies on only the few conventions given in the next section.

What the skeleton relies on

  • project : A link to ../../../, the directory that holds this project and its siblings. It comes with the skeleton. Links to dependencies are made through it, so they are relative and stay correct in every clone.
  • <name>.init : A bash script that every role setup sources, for every role, each time a person takes on a role. It puts the dependency into the environment, typically by adding to PATH or exporting variables.
  • <name>.org or <name>.html : Notes on how the dependency was installed, so that each team member can repeat the installation after cloning. Short notes may instead be comments at the top of <name>.init.
  • <name>.install : Optional. A script that carries out the installation, where it can be automated. A person runs it; setup never does.
  • .gitignore : Belongs to the administrator. It decides which of the files in the directory are tracked.

Files for one dependency share a base name, so that Python.init, Python.org, and the link they describe sit together in a listing.

Steps

Install the dependency beside the project

Download, clone, or extract the dependency into the directory that holds the project, so that it sits as a sibling of the project directory. Build it there if it needs building.

Link it

Make the link through the project link. The word project in the link target is literal.

> cd $REPO_HOME/shared/project-dependency > ln -s project/<dependency directory> <name>

Write the init file

Write <name>.init in the same directory. Because it runs on every setup for every role, keep it to setting the environment:

  • Make it quick, and safe to run any number of times.
  • Do not install, build, or download anything from it.
  • Test that the dependency is present before using it, so that a clone without the dependency still sets up.
  • Print nothing in normal use. A notice for the administrator role, when the dependency is missing, is fine.

Python.init, which comes with the skeleton, is an example:

if [[ -d "$REPO_HOME/shared/project-dependency/Python-3.12.3/bin" ]]; then PATH="$REPO_HOME/shared/project-dependency/Python-3.12.3/bin:$PATH" else if [[ "$ROLE" == "administrator" ]]; then echo "Notice: Local Python-3.12.3 bin not found. Using system Python." fi fi

Write the installation notes

Record what was installed, where it came from, and the commands used, in <name>.org, <name>.html, or comments in the init file. A team member who has cloned the project follows these notes to install the dependency, and then recreates the link if it is not tracked.

Decide what is tracked

The skeleton's .gitignore tracks itself, the project link, and files ending in .init, .install, .org, and .html. Everything else in the directory is ignored. To track a dependency's link, so that it arrives with every clone, add a line naming it:

!<name>

A tracked link points at nothing until the dependency is installed beside the project, which is why init files test for the dependency before using it.

Commit

Add the init file, the notes, the .gitignore change, and any tracked link, then commit.
